Découvrir dbt

TipTestez au fur et à mesure

dbt s’utilise dans un terminal, pas dans un notebook. Le plus simple est d’ouvrir un service VSCode sur SSP Cloud, puis d’ouvrir un terminal (menu Terminal → New Terminal) pour lancer les commandes de cette page au fil de la lecture.

Vous pouvez aussi travailler sur votre ordinateur, dans VSCode, après avoir installé dbt (voir la section Installation).

Par le passé, vous avez écrit des requêtes SQL pour filtrer, joindre et agréger des données. Une requête, c’est simple. Mais imaginez une équipe data avec 2 000 requêtes qui dépendent les unes des autres : laquelle lancer en premier ? Qui a modifié celle-ci ? Le chiffre d’affaires du tableau de bord est-il encore juste ? dbt a été créé pour répondre à ces questions.

dbt, c’est quoi ?

dbt signifie data build tool. C’est un outil en ligne de commande qui sert à transformer des données déjà présentes dans une base, en écrivant uniquement des requêtes SELECT.

Concrètement, vous écrivez des fichiers .sql qui contiennent chacun une requête SELECT. dbt se charge du reste :

  • il transforme chaque requête en table ou en vue dans la base ;
  • il comprend dans quel ordre lancer les requêtes, grâce aux dépendances entre elles ;
  • il teste les données (pas de doublons, pas de valeurs manquantes…) ;
  • il génère une documentation du projet, avec le schéma des dépendances.
Notedbt ne fait pas les calculs lui-même

dbt n’est pas une base de données. Il compile vos fichiers en SQL, puis il envoie ce SQL à la base (DuckDB, PostgreSQL, BigQuery, Snowflake…), qui fait tout le travail. Les données ne transitent jamais par dbt : elles restent dans la base.

Un outil de transformation pour l’ELT

Pour qu’une donnée arrive dans un tableau de bord, il faut trois étapes :

Étape En anglais Exemple
Extraire Extract Interroger une API, lire l’export d’un logiciel
Charger Load Écrire ces données brutes dans la base
Transformer Transform Nettoyer, joindre, agréger pour répondre à une question métier

Il existe deux façons d’organiser ces étapes :

  • ETL : on transforme les données avant de les charger, par exemple dans un script Python, et on n’enregistre dans la base que le résultat final.
  • ELT : on charge d’abord les données brutes dans la base, puis on les transforme dans la base, en SQL.

dbt est l’outil du T de l’ELT. Il ne sait ni appeler une API, ni lire un fichier sur un serveur distant, ni déplacer des données d’une base à une autre. Ces étapes sont confiées à d’autres outils : un script Python, Airbyte, Fivetran, dlt… dbt intervient une fois que les données brutes sont dans la base.

NoteUn peu d’histoire : pourquoi l’ETL était la norme avant ?

Des années 1990 aux années 2010, l’ETL est le standard. Les entreprises utilisent des outils comme Informatica PowerCenter, IBM DataStage, Microsoft SSIS, puis Talend en open source : on y dessine les flux de données à la souris, sans écrire de code. Plusieurs raisons expliquent ce choix :

  • L’entrepôt de données coûte très cher. Il tourne sur des serveurs physiques achetés par l’entreprise, et le coût total (matériel et licences) peut atteindre plusieurs millions de dollars. Le stockage est rare, mais le calcul aussi : chaque traitement lancé dans l’entrepôt ralentit les requêtes des utilisateurs. On transforme donc les données sur un serveur à part, et on ne charge dans l’entrepôt que des données nettoyées et agrégées1.
  • La structure est définie avant d’écrire les données. Les entrepôts suivent des modèles stricts (schémas en étoile notamment) : une donnée doit être propre et au bon format avant d’entrer. Il n’existe pas de zone pour stocker du « brut ».
  • Les sources sont très hétérogènes. Mainframes, fichiers plats, formats propriétaires : il faut de toute façon convertir avant de charger, et les outils ETL proposent des connecteurs pour tout.
  • Les traitements tournent la nuit, par lots. Ne charger que le nécessaire permet de tenir dans la fenêtre de traitement nocturne.

Ce qui a changé la donne :

  1. Hadoop et Amazon S3, en 2006 : la même année, deux innovations rendent le stockage massif abordable. Hadoop, projet open source inspiré de deux publications de Google et développé notamment chez Yahoo!, permet de stocker et de traiter d’énormes volumes de données sur des grappes de serveurs ordinaires et bon marché2. Amazon S3, lancé en mars 2006, propose un stockage en ligne payé à l’usage, sans serveur à acheter ni à administrer3. S3 et ses équivalents (Google Cloud Storage, Azure Blob, MinIO sur SSP Cloud) deviendront le socle de la plupart des data lakes.
  2. Les data lakes, autour de 2010 : le terme, popularisé par James Dixon, alors directeur technique de Pentaho4, donne un nom à cette nouvelle approche : stocker d’abord toutes les données brutes, puis décider plus tard comment les exploiter.
  3. Les entrepôts cloud, au début des années 2010 : BigQuery est annoncé en 20105, Amazon Redshift devient disponible en 2013 pour moins de 1 000 dollars par téraoctet et par an6, et Snowflake est fondé en 2012 sur l’idée de séparer le stockage et le calcul, facturés et dimensionnés indépendamment7. La puissance se loue à la demande : transformer directement dans la base devient rapide et bon marché.
  4. Des outils pensés pour l’ELT : dbt est créé en 2016 par Tristan Handy, Drew Banin et Connor McArthur, chez Fishtown Analytics, justement pour profiter de ces entrepôts cloud8.

La philosophie de dbt

dbt applique aux données les bonnes pratiques des développeurs :

  • Tout est du code. Une transformation est un fichier texte, versionné avec git. On sait qui a changé quoi, et quand.
  • Un modèle = un SELECT. Pas de CREATE TABLE, pas de INSERT : vous décrivez le résultat voulu, dbt s’occupe de le construire.
  • Des briques réutilisables. Plutôt qu’une requête géante de 300 lignes, on enchaîne de petits modèles qui s’appuient les uns sur les autres.
  • On teste. Une donnée fausse dans un tableau de bord est pire qu’une absence de donnée. Les tests détectent les problèmes avant qu’ils n’arrivent chez les métiers.
  • On documente. La documentation vit à côté du code, et dbt la transforme en site web consultable.

Ce métier, à mi-chemin entre l’analyste et le développeur, a même reçu un nom : l’analytics engineering.

Quel dbt ?

« dbt » désigne à la fois un outil et une entreprise, dbt Labs, qui le développe. Elle en propose plusieurs versions :

Version Licence Prix Usage
dbt OSS Open source (Apache 2.0) Gratuit L’outil en ligne de commande, entièrement open source : c’est celui que nous utilisons
dbt Propriétaire Gratuit Le même outil, avec des fonctions en plus : analyse du SQL avant exécution, autocomplétion, extension VS Code
dbt platform Propriétaire Payant Une version hébergée : éditeur en ligne, planification des exécutions, interface web
dbt Core Open source (Apache 2.0) Gratuit L’ancienne version (v1), en Python, encore très présente en entreprise
Notedbt OSS ou dbt : quelle différence ?

Pensez à Chromium et Google Chrome : dbt OSS est le moteur, entièrement open source. dbt reprend ce même moteur et y ajoute des briques fermées qui aident à écrire le code. Les commandes et les projets sont identiques : tout ce que vous apprenez ici fonctionne avec l’une comme avec l’autre, et avec dbt Core.

Ce modèle s’appelle l’open core : le cœur de l’outil est libre, pour fédérer une communauté, tandis que les fonctions les plus confortables restent fermées ou payantes, pour faire vivre l’entreprise.

Attention enfin : gratuit ne veut pas dire libre. Un logiciel libre donne à chacun le droit de lire, modifier et redistribuer son code, et une version publiée sous licence libre le reste : si l’éditeur change de cap, la communauté peut reprendre ce code et le faire vivre ailleurs. Un logiciel propriétaire gratuit, lui, s’utilise selon les conditions de son éditeur, qui peut les changer à la version suivante.

TipLibre aujourd’hui, mais demain ?

Une licence libre protège le code déjà publié, pas l’avenir du projet. En 2023, HashiCorp a publié les nouvelles versions de Terraform sous une licence qui n’est plus open source : la communauté a repris la dernière version libre pour créer OpenTofu. Plus récemment, MinIO, un stockage objet très utilisé, a retiré des fonctions de son édition gratuite puis cessé de la maintenir. Avant d’adopter un outil, regardez donc aussi qui le maintient et comment il gagne sa vie.

Installation

uv tool install dbt-oss  # installe la commande dbt, en open source
dbt --version            # doit commencer par 2.

uv tool install installe dbt comme un outil : la commande dbt est disponible partout dans le terminal, sans être ajoutée aux dépendances d’un projet Python. C’est logique, car on ne fait jamais import dbt : on le lance dans un terminal, et un projet dbt contient des fichiers .sql et .yml, pas du code Python.

WarningUne seule version de dbt à la fois

dbt-oss, dbt et dbt-core fournissent tous la même commande dbt : ne les installez pas dans le même environnement, ils se gêneraient mutuellement. Si vous rejoignez une équipe en dbt Core (v1), installez sa version avec son adaptateur : uv add dbt-core dbt-duckdb.

La structure d’un projet

La commande dbt init crée un nouveau projet :

uv run dbt init commandes
commandes/
├── dbt_project.yml     # la carte d'identité du projet
├── models/             # vos transformations (.sql) et leur description (.yml)
├── seeds/              # de petits référentiels CSV (pas vos données !)
├── tests/              # vos tests personnalisés (.sql)
├── macros/             # des fonctions réutilisables
├── snapshots/          # l'historisation de tables qui changent
├── analyses/           # des requêtes d'analyse
└── README.md

Deux dossiers apparaîtront au premier lancement, à ne jamais versionner (ajoutez-les au .gitignore) :

  • target/ : le SQL compilé par dbt et les résultats d’exécution ;
  • dbt_packages/ : les paquets externes installés avec dbt deps.

Au début, vous n’utiliserez que models/ et tests/.

dbt_project.yml : la configuration du projet

name: 'commandes'
version: '1.0.0'
profile: 'commandes'          # le profil de connexion à utiliser

models:
  commandes:
    staging:
      +materialized: view     # les modèles de models/staging/ seront des vues
    marts:
      +materialized: table    # ceux de models/marts/ seront des tables

profiles.yml : la connexion à la base

Ce fichier dit à dbt où se connecter. Avec DuckDB, la base est un simple fichier :

commandes:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: commandes.duckdb

Pour BigQuery ou PostgreSQL, on y trouverait un projet, un serveur, un identifiant… Comme d’habitude, les mots de passe ne s’écrivent jamais en clair : dbt sait lire les variables d’environnement avec { env_var('DB_PASSWORD') }.

WarningOù ranger profiles.yml ?

Par défaut, dbt cherche ce fichier dans ~/.dbt/, en dehors du projet, justement pour qu’il ne finisse pas sur GitHub avec des identifiants. Pour un projet DuckDB local sans secret, on peut le laisser dans le projet et lancer les commandes avec --profiles-dir ..

Avant dbt : charger les données brutes

Rappelez-vous : dbt est le T de l’ELT. Il ne sait pas lire un fichier CSV en ligne ou posé sur votre disque, ni interroger une API. Avant de l’utiliser, il faut donc que les données brutes soient déjà dans la base. C’est le rôle de l’étape EL, confiée à un autre outil.

Pour illustrer, prenons un mini-exemple de commandes fournisseurs, avec deux fichiers CSV disponibles en ligne. Le projet guidé reprendra tout cela en détail sur un vrai jeu de données.

commandes.csv :

id_commande,id_fournisseur,date_commande,date_livraison,quantite
1,F01,2026-09-01,2026-09-04,120
2,F02,2026-09-02,2026-09-10,80
3,F01,2026-09-05,2026-09-07,200
4,F03,2026-09-06,2026-09-15,50
5,F02,2026-09-08,2026-09-12,150

fournisseurs.csv :

id_fournisseur,nom,delai_promis_jours
F01,Acier SA,3
F02,BoisPlus,5
F03,Plastico,7

Ici, notre outil d’EL est un petit script Python qui utilise DuckDB (uv add duckdb). DuckDB sait lire un fichier directement depuis son adresse web, sans qu’on ait à le télécharger :

# charger_donnees.py
import duckdb

URL = "https://minio.lab.sspcloud.fr/fabienhos/exemple_dbt"

connexion = duckdb.connect("commandes.duckdb")
connexion.sql("CREATE SCHEMA IF NOT EXISTS raw")

connexion.sql(f"CREATE OR REPLACE TABLE raw.commandes AS SELECT * FROM read_csv('{URL}/commandes.csv')")
connexion.sql(f"CREATE OR REPLACE TABLE raw.fournisseurs AS SELECT * FROM read_csv('{URL}/fournisseurs.csv')")

print(connexion.sql("SELECT count(*) AS nb_commandes FROM raw.commandes"))
connexion.close()
┌──────────────┐
│ nb_commandes │
│    int64     │
├──────────────┤
│            5 │
└──────────────┘

Les données sont copiées telles quelles dans un schéma raw : aucun nettoyage, aucun calcul. Tout le reste sera le travail de dbt.

NoteUne f-string dans du SQL ?

Dans la page sur les bases de données, nous avons vu qu’il ne faut jamais construire une requête avec une f-string. La règle concerne les valeurs qui viennent de l’extérieur (un utilisateur, un formulaire, un fichier), qui pourraient contenir du SQL malveillant. Ici, l’adresse est écrite dans notre propre code : il n’y a aucun risque.

WarningFermez la connexion

DuckDB n’autorise qu’un seul programme à écrire dans un fichier de base à la fois. Si le script ne ferme pas sa connexion (ou si un notebook garde la base ouverte), dbt ne pourra pas y accéder.

Déclarer les sources

dbt doit savoir que ces tables existent. On les déclare comme sources dans un fichier .yml :

# models/staging/_sources.yml
version: 2

sources:
  - name: raw            # le schéma où le script a chargé les tables
    tables:
      - name: commandes
      - name: fournisseurs

Les modèles : un fichier, un SELECT

Un modèle est un fichier .sql dans models/. Son nom de fichier devient le nom de la table ou de la vue créée.

-- models/staging/stg_commandes.sql
select
    id_commande,
    id_fournisseur,
    cast(date_commande as date) as date_commande,
    cast(date_livraison as date) as date_livraison,
    quantite
from {{ source('raw', 'commandes') }}

source() et ref() : le cœur de dbt

{ source('raw', 'commandes') } remplace le nom de la table. Cette syntaxe entre doubles accolades vient de Jinja, un langage de gabarits que dbt utilise pour rendre le SQL dynamique.

Il existe deux fonctions de ce type :

  • source() désigne une table brute, chargée par un autre outil et déclarée dans les sources ;
  • ref() désigne un autre modèle dbt.

Elles font deux choses :

  1. Au moment de la compilation, dbt les remplace par le vrai nom de la table. Le fichier compilé dans target/ contient :

    from "commandes"."raw"."commandes"

  2. Surtout, dbt enregistre la dépendance : stg_commandes dépend de la source raw.commandes. Avec toutes les dépendances, il construit un graphe (le DAG) et sait dans quel ordre tout lancer.

Un modèle peut s’appuyer sur d’autres modèles :

-- models/marts/performance_fournisseurs.sql
with commandes as (
    select * from {{ ref('stg_commandes') }}
),

fournisseurs as (
    select * from {{ ref('stg_fournisseurs') }}
)

select
    f.nom_fournisseur,
    count(*) as nb_commandes,
    avg(c.date_livraison - c.date_commande) as delai_moyen_jours,
    sum(case when c.date_livraison - c.date_commande > f.delai_promis_jours
             then 1 else 0 end) as nb_retards
from commandes c
join fournisseurs f using (id_fournisseur)
group by f.nom_fournisseur
raw.commandes ────> stg_commandes ─────┐
                                       ├──> performance_fournisseurs
raw.fournisseurs ─> stg_fournisseurs ──┘
WarningJamais de nom de table en dur

Écrire from raw.commandes ou from main.stg_commandes fonctionnerait aussi… jusqu’au jour où le projet passe d’une base de test à la base de production, avec d’autres noms de schémas. Et dbt ne verrait pas la dépendance : il pourrait lancer les modèles dans le mauvais ordre. Toujours source() ou ref().

Les couches d’un projet

La documentation officielle recommande d’organiser les modèles en trois couches :

Couche Préfixe Rôle
Staging stg_ Un modèle par table brute : renommer, typer, nettoyer. Pas de jointure.
Intermediate int_ Étapes de préparation : jointures, calculs intermédiaires.
Marts fct_, dim_ ou nom métier Les tables finales, prêtes pour les tableaux de bord et les analyses.

Vous croiserez aussi les noms bronze, silver et gold (architecture médaillon) : c’est la même idée, du brut vers le prêt à l’emploi.

Les matérialisations

La matérialisation décide ce que dbt crée dans la base pour un modèle :

Matérialisation Ce que dbt crée Quand l’utiliser
view Une vue : la requête est relancée à chaque lecture Par défaut, modèles légers (staging)
table Une table : le résultat est calculé et stocké Modèles lus souvent ou coûteux (marts)
ephemeral Rien : le modèle est injecté dans les modèles qui l’utilisent Petites étapes intermédiaires
incremental Une table complétée à chaque lancement, sans tout recalculer Gros volumes qui grossissent chaque jour

Et les seeds ?

Vous avez vu passer un dossier seeds/ dans la structure du projet. Les seeds sont de petits fichiers CSV rangés dans le projet, que dbt seed charge dans la base. On les appelle avec ref().

Ce n’est pas un moyen de charger vos données : ils servent uniquement aux petits référentiels que l’équipe maintient elle-même et veut versionner avec le code. Une table de correspondance de codes pays, une liste de jours fériés, les délais promis par fournisseur…

TipSeed ou source ?
  • La donnée existe déjà dans la base, ou elle arrive d’une application, d’une API, d’un fichier d’export : c’est une source, chargée par un outil d’EL.
  • C’est un petit référentiel qui n’existe nulle part ailleurs et change rarement : c’est un seed.

Tester ses données

Les tests génériques

Les tests se déclarent dans un fichier .yml, à côté des modèles. dbt en fournit quatre :

# models/staging/_staging.yml
version: 2

models:
  - name: stg_commandes
    description: "Une ligne par commande fournisseur."
    columns:
      - name: id_commande
        description: "Identifiant unique de la commande."
        data_tests:
          - unique
          - not_null
      - name: id_fournisseur
        data_tests:
          - relationships:
              arguments:
                to: ref('stg_fournisseurs')
                field: id_fournisseur
Test Vérifie que…
unique la colonne ne contient aucun doublon
not_null la colonne ne contient aucune valeur manquante
accepted_values les valeurs appartiennent à une liste donnée
relationships chaque valeur existe dans une autre table (ici, chaque commande a un fournisseur connu)

Les tests personnalisés

Un test personnalisé est une requête rangée dans tests/ qui cherche les lignes problématiques. Si elle renvoie au moins une ligne, le test échoue :

-- tests/assert_livraison_apres_commande.sql
-- Une livraison ne peut pas avoir lieu avant la commande.
select *
from {{ ref('stg_commandes') }}
where date_livraison < date_commande

🧠 À vous de réfléchir

Imaginez que le fichier des commandes contienne une ligne de plus :

6,F09,2026-09-09,2026-09-08,10

Le fournisseur F09 n’existe pas dans data/fournisseurs.csv. Quels tests vont échouer ? Et que va-t-il arriver au modèle performance_fournisseurs ?

Tip💡 Voir la solution

Deux tests échouent :

  • relationships : F09 n’existe pas dans stg_fournisseurs ;
  • assert_livraison_apres_commande : la livraison (le 8) précède la commande (le 9).
3 of 7 FAIL 1 assert_livraison_apres_commande .................................. [FAIL 1 in 0.03s]
6 of 7 FAIL 1 relationships_stg_commandes_id_fournisseur__id_fournisseur__ref_stg_fournisseurs_  [FAIL 1 in 0.03s]
7 of 7 SKIP relation main.performance_fournisseurs ............................. [SKIP]
...
Done. PASS=4 WARN=0 ERROR=2 SKIP=1 NO-OP=0 REUSED=0 TOTAL=7

Et performance_fournisseurs n’est pas construit (SKIP) : avec dbt build, un modèle n’est pas lancé si les tests des modèles dont il dépend échouent. Le tableau de bord garde la dernière version correcte au lieu d’afficher des chiffres faux. C’est exactement le but.

Les commandes de base

Commande Ce qu’elle fait
dbt init <nom> Crée un nouveau projet
dbt debug Vérifie l’installation et la connexion à la base
dbt seed Charge les CSV de seeds/ dans la base
dbt run Construit les modèles (tables et vues)
dbt test Lance les tests
dbt build Fait tout, dans l’ordre du graphe : seeds, modèles, tests, snapshots
dbt compile Génère le SQL dans target/, sans rien exécuter
dbt show -s <modèle> Affiche un aperçu du résultat d’un modèle
dbt ls Liste les éléments du projet
dbt docs generate puis dbt docs serve Génère et ouvre la documentation du projet
dbt deps Installe les paquets externes
dbt clean Supprime target/ et dbt_packages/

Au quotidien, trois commandes suffisent, une fois les données brutes chargées : dbt build pour tout construire et tester, dbt run -s <modèle> pour relancer ce sur quoi vous travaillez, et dbt show -s <modèle> pour vérifier le résultat. Vous les pratiquerez en détail dans le projet guidé.

Sélectionner une partie du projet

Sur un vrai projet, on ne relance pas tout à chaque modification. L’option --select (ou -s) choisit ce qu’on lance :

dbt run -s stg_commandes               # un seul modèle
dbt run -s stg_commandes+              # ce modèle et tout ce qui en dépend
dbt run -s +performance_fournisseurs   # ce modèle et tout ce dont il dépend
dbt build -s staging                   # tout le dossier models/staging/
Warning

Vous trouverez dans d’anciens tutoriels l’option --models ou -m. Elle a été remplacée par --select et provoque désormais une erreur avec dbt v2.

Pour aller plus loin

NotePartie avancée, dépliez si vous êtes à l’aise

Une fois les bases acquises, voici ce que vous croiserez rapidement :

  • Les macros : des fonctions Jinja, rangées dans macros/, pour éviter de recopier le même morceau de SQL dans plusieurs modèles.
  • Les paquets : des macros et des tests prêts à l’emploi, déclarés dans packages.yml et installés avec dbt deps. Le plus connu est dbt_utils.
  • Les snapshots : garder l’historique d’une table qui change, par exemple l’adresse d’un client avant et après un déménagement.
  • Les modèles incrémentaux : ne traiter que les nouvelles lignes à chaque lancement, indispensable sur de gros volumes.
  • Les environnements : plusieurs outputs dans profiles.yml (dev, prod), et dbt build --target prod pour choisir.

ImportantÀ retenir
  • dbt (data build tool) transforme des données déjà présentes dans une base. C’est le T de l’ELT : il n’extrait ni ne charge rien, un autre outil (ici, un script Python) s’en charge avant lui.
  • Un modèle est un fichier .sql qui contient un seul SELECT ; dbt en fait une vue ou une table.
  • source() désigne les tables brutes, ref() relie les modèles entre eux : dbt en déduit l’ordre d’exécution. Jamais de nom de table en dur.
  • On organise les modèles en couches : staging (nettoyer), intermediate (préparer), marts (servir).
  • Les tests (unique, not_null, relationships, accepted_values ou personnalisés) bloquent les données fausses avant qu’elles n’atteignent les tableaux de bord.
  • dbt_project.yml configure le projet, profiles.yml la connexion, qui ne contient jamais de mot de passe en clair.
  • dbt build lance tout dans l’ordre : seeds, modèles et tests.
